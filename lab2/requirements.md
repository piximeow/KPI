# Вимоги до UC5 «Оформити замовлення»

Функціональні вимоги написані в EARS лише під сценарії з [`features/uc5-place-order.feature`](features/uc5-place-order.feature); у дужках — сценарії, з яких вимога випливає (повна матриця: [`traceability.md`](traceability.md)). Назви полів і статусів — як у моделі lab1. «Підтвердження» — натискання кнопки «Підтвердити замовлення».

## Функціональні вимоги (EARS)

| ID | Вимога | Сценарії |
|----|--------|----------|
| REQ-01 | WHEN відвідувач підтверджує замовлення і жодна з умов REQ-09, REQ-10, REQ-14, REQ-15, REQ-18 не спрацювала, система SHALL в одній транзакції створити `order` (`order_status` = `new`, `address_id` обраної адреси, `ordered_at` = час підтвердження), по одному `order_item` на кожен товар кошика (`quantity` з кошика, `unit_price` = поточна `price`) і `payment` (`payment_status` = `pending`, обраний `payment_method`, `payment_amount` = сума `quantity × unit_price`). | S1, S2, S5, S8, S9 |
| REQ-02 | WHEN створено `order`, система SHALL у тій самій транзакції зменшити `stock_quantity` кожного товару на `quantity` його `order_item`. | S1 |
| REQ-03 | WHEN створено `order`, система SHALL показати номер замовлення і: для `cash_on_delivery` — суму до сплати; для `bank_transfer` — реквізити та граничний час оплати (`ordered_at` + 72 год); для `card` — перенаправити відвідувача на сторінку платіжного шлюзу. | S1, S2, S5, S9 |
| REQ-04 | WHEN платіжний шлюз повідомляє про успішний платіж для `payment` зі статусом `pending`, `order` якого має статус `new`, система SHALL встановити `payment_status` = `succeeded`, `paid_at` = час отримання повідомлення і `order_status` = `paid`. | S2 |
| REQ-05 | IF платіжний шлюз повідомляє результат для `payment`, статус якого не `pending`, або для `payment_id`, якого немає, THEN система SHALL не змінювати ні `payment`, ні `order`. | S2 |
| REQ-06 | WHEN платіжний шлюз повідомляє про відмову для `payment` зі статусом `pending`, система SHALL встановити `payment_status` = `failed` і не змінювати `order_status`; якщо `order` має статус `new`, — показати відвідувачу повідомлення про відмову та кнопку «Оплатити ще раз». | S3 |
| REQ-07 | WHEN відвідувач натискає «Оплатити ще раз» для `order` зі статусом `new` до граничного часу оплати, система SHALL створити новий `payment` (`card`, `pending`, той самий `payment_amount`), не змінюючи попередніх `payment`. | S3 |
| REQ-08 | WHILE `order` має статус `new` і жоден його `payment` не має статусу `succeeded`, WHEN від `ordered_at` минуло 30 хв для `card` або 72 год для `bank_transfer`, система SHALL встановити `order_status` = `cancelled`, усім `payment` `bank_transfer` зі статусом `pending` — `failed` (картковий `payment` лишається `pending` до повідомлення шлюзу), і повернути `quantity` кожного `order_item` у `stock_quantity`. | S4, S10 |
| REQ-09 | IF на момент підтвердження `quantity` хоча б одного товару в кошику більша за його `stock_quantity`, THEN система SHALL не створювати замовлення і показати для кожного такого товару доступну кількість. | S7 |
| REQ-10 | IF на момент підтвердження `price` хоча б одного товару відрізняється від ціни, показаної в кошику, THEN система SHALL не створювати замовлення, показати нові ціни й нову суму і створити замовлення лише після повторного підтвердження. | S8 |
| REQ-11 | WHERE відвідувач увійшов як клієнт, система SHALL запропонувати вибрати одну з `address` цього `customer` або додати нову. | S1, S2 |
| REQ-12 | WHERE відвідувач не увійшов в акаунт, система SHALL вимагати `first_name`, `last_name`, `email`, `country`, `city`, `street_line`, `postal_code`; `phone` — необов'язковий. | S5, S6, S9 |
| REQ-13 | WHEN гість, email якого немає серед `customer`, підтверджує замовлення, система SHALL у тій самій транзакції, що й REQ-01, створити гостьовий запис `customer` (`registered_at` = час підтвердження) і його `address`. | S5 |
| REQ-14 | IF гість вводить `email` `customer`, для якого є акаунт, THEN система SHALL не створювати замовлення, показати пропозицію увійти й зберегти вміст кошика. | S6 |
| REQ-15 | IF обов'язкове поле з REQ-12 порожнє або `email` не має вигляду `локальна-частина@домен`, THEN система SHALL показати помилку біля цього поля і не створювати замовлення. | — (UC6, див. матрицю) |
| REQ-16 | WHEN гість, email якого належить гостьовому запису `customer` без акаунта, підтверджує замовлення, система SHALL не створювати нового `customer`, не змінювати поля наявного, створити нову `address` цього `customer` у транзакції REQ-01 і не показувати гостю попередніх замовлень і адрес. | S9 |
| REQ-17 | IF платіжний шлюз повідомляє про успішний платіж для `payment` зі статусом `pending`, `order` якого має статус `cancelled`, THEN система SHALL встановити `payment_status` = `succeeded` і `paid_at` = час повідомлення, залишити `order_status` = `cancelled`, не змінювати `stock_quantity` і показати це замовлення Менеджеру з позначкою «потрібне повернення коштів». | S10 |
| REQ-18 | IF на момент підтвердження сума `quantity × price` усіх товарів кошика дорівнює 0.00, THEN система SHALL не створювати замовлення і показати повідомлення, що замовлення має містити хоча б один платний товар. | S11 |

## Нефункціональні вимоги (NFR)

NFR не наносяться на діаграму й не трасуються.

| ID | Категорія | Вимога | Як перевірити |
|----|-----------|--------|---------------|
| NFR-01 | Продуктивність | Час від підтвердження до показу номера замовлення або перенаправлення на шлюз: p95 ≤ 2 с, p99 ≤ 4 с за навантаження до 100 одночасних оформлень і до 300 замовлень за годину, каталог до 10 000 товарів. | навантажувальний тест 30 хв |
| NFR-02 | Цілісність | За 50 одночасних підтверджень на товар із `stock_quantity` = N створюються замовлення сумарно не більше ніж на N одиниць; `stock_quantity` ніколи не стає < 0. | конкурентний тест, 20 прогонів |
| NFR-03 | Своєчасність | Повідомлення шлюзу обробляється за ≤ 3 с (p95); скасування за REQ-08 відбувається не пізніше ніж через 60 с після спливу терміну. | тест із підставним шлюзом і зсунутим годинником |
| NFR-04 | Доступність сервісу | Оформлення замовлення доступне 99,5 % часу за календарний місяць (≤ 3 год 39 хв простою); планові роботи — лише 01:00–06:00 за Києвом. | моніторинг раз на 1 хв |
| NFR-05 | Безпека | Дані картки вводяться лише на сторінці шлюзу; система не отримує й не зберігає номер картки чи CVV. Увесь трафік — HTTPS, TLS ≥ 1.2. Повідомлення шлюзу без дійсного підпису (HMAC-SHA256) відхиляються і не змінюють даних. | огляд схеми БД і логів; тест із підробленим підписом |
| NFR-06 | Безпека | Не більше 10 підтверджень замовлення з однієї IP-адреси за 1 хв для гостей; 11-те отримує відмову з повідомленням «спробуйте за хвилину». | автотест |
| NFR-07 | Пристрої | Chrome, Edge, Firefox, Safari — дві останні мажорні версії; Android ≥ 11, iOS ≥ 16; ширина екрана від 360 px без горизонтальної прокрутки форми. | ручний прогін S1, S2, S5 на кожній платформі |
| NFR-08 | Мова й формати | Інтерфейс українською; ціни в гривнях з двома знаками після коми (`2 400,00 грн`); час показується за Europe/Kyiv, зберігається в UTC. | перевірка екранів S1–S8 |
| NFR-09 | Доступність інтерфейсу | Форма оформлення відповідає WCAG 2.1 рівня AA. | автоматичний аудит axe: 0 порушень рівнів A/AA |
| NFR-10 | Технологія | Веб-застосунок; дані — у PostgreSQL ≥ 15 за схемою, отриманою з ER-моделі lab1 без додавання чи вилучення сутностей. | огляд схеми проти `lab1/model.md` |

## Поза обсягом

| Що не робимо | Чому |
|--------------|------|
| Кошик як збережені дані (UC3) | у моделі lab1 немає сутності кошика; кошик зберігається на боці браузера й лише передається в UC5. |
| Вхід, паролі, відновлення доступу | у `customer` немає облікових даних; автентифікація — окрема підсистема, для UC5 вхід — передумова. |
| Обробка, відвантаження й доставка (статуси `shipped`, `delivered`, UC12) | це наступний прецедент Менеджера; служба доставки в цій роботі нічого не ініціює. |
| Повернення коштів (статус `refunded`) | потребує окремого процесу з менеджером і шлюзом, не належить до оформлення; UC5 лише позначає замовлення за REQ-17. |
| Підтвердження банківського переказу | виконує Менеджер в UC12; в UC5 лише створюється `payment` `pending` і діє таймаут REQ-08. |
| Знижки, промокоди, доставка за гроші | у моделі немає полів для них; `payment_amount` = сума позицій. |
| Замовлення лише з безкоштовних товарів | `payment_amount` > 0 у моделі lab1, а замовлення без `payment` не має способу оплати; безкоштовний товар можна замовити лише разом із платним (REQ-18). |
| Кілька валют і мов | магазин працює в Україні, NFR-08. |
| Часткова оплата, кілька успішних платежів | одне замовлення оплачується одним `payment` повністю; повтори — лише після `failed`. |
| Повернення гостя до неоплаченого замовлення після закриття сторінки | гість не має UC9; повторити оплату він може лише зі сторінки результату (REQ-06, REQ-07), посилання в листі — частина сповіщень. |
| Скасування замовлення клієнтом або менеджером | окремий прецедент; в UC5 скасування відбувається лише за таймаутом (REQ-08). |
| Видалення адрес і відгуки (UC8, UC10) | не належать до UC5; адресу з замовленнями змінювати не можна (lab1, ADR 0002). |
| Листи й SMS-сповіщення | канал сповіщення — деталь реалізації; результат показується на сторінці замовлення. |
