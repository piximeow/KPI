# Вимоги до UC5 «Оформити замовлення»

Функціональні вимоги написані в EARS лише під сценарії з [`features/uc5-place-order.feature`](features/uc5-place-order.feature); у колонці «Сценарії» — сценарії, з яких вимога випливає (повна матриця: [`traceability.md`](traceability.md)). Назви полів і статусів — як у моделі lab1; «акаунт» і «гостьовий запис» — як у `spec.md`, розділ «Терміни». **Система** — увесь веб-застосунок, зокрема інтерфейс у браузері, де зберігається кошик.

## Визначення й константи

| Позначення | Значення |
|------------|----------|
| `T_CARD` | 30 хв — термін оплати карткою від `ordered_at` |
| `T_BANK` | 72 год — термін оплати переказом від `ordered_at` |
| `T_RETRY_MIN` | 5 хв — найменший залишок терміну, за якого можна повторити оплату |
| `T_CARD_FINAL` | 24 год від `ordered_at` — після цього шлюз уже не підтверджує оплату (умова договору зі шлюзом) |
| `T_DEDUP` | 24 год — скільки діє ідентифікатор оформлення |
| `T_REFRESH` | 5 с — період оновлення сторінки у стані «Оплата обробляється» |
| `RATE_MAX` | 10 підтверджень за ковзні 60 с |
| Граничний час оплати | `ordered_at` + `T_CARD` (`card`) або + `T_BANK` (`bank_transfer`); для `cash_on_delivery` немає |
| Останній `payment` | `payment` замовлення з найбільшим `payment_id` |
| Підтвердження | натискання «Підтвердити замовлення»; інтерфейс кошика передає разом із ним ідентифікатор оформлення і кожен товар один раз (кількості одного товару сумуються) з кількістю й ціною, які бачив відвідувач |
| Ідентифікатор оформлення | випадковий ключ, який система видає при відкритті форми й тримає в сесії (не в доменних даних, NFR-14) |
| Нормалізований email | без пробілів на краях, у нижньому регістрі; так email зберігається в `customer` і так порівнюється, тому UQ моделі діє без урахування регістру |

**Перевірки підтвердження** виконуються в такому порядку; показується результат лише першої непройденої (REQ-25): V0 — кошик (REQ-26) → V1 — поля (REQ-15) → V2 — email з акаунтом (REQ-14) → V3 — нульова сума (REQ-18) → V4 — ціна (REQ-10) → V5 — залишок (REQ-09). Перевірку дубля (REQ-19) система робить перед V1.

**Правила полів** (REQ-12, REQ-15): `first_name`, `last_name`, `city` — 1–50 символів після обрізання пробілів; `street_line` — 1–100; `country` — «Україна»; `postal_code` — рівно 5 цифр; `email` — до 254 символів, рівно один `@`, обидві частини непорожні, у доменній частині є крапка; `phone` — порожній або `+380` і 9 цифр.

**Стани сторінки замовлення** (REQ-20):

| `order_status` | Останній `payment` | Що бачить відвідувач |
|----------------|--------------------|----------------------|
| `new` | `card`, `pending` | «Оплата обробляється», без кнопок оплати |
| `new` | `card`, `failed` | «Оплату відхилено», залишок терміну; кнопка «Оплатити ще раз», якщо до граничного часу ≥ `T_RETRY_MIN` |
| `new` | `cash_on_delivery`, `pending` | «Оплата при отриманні», сума |
| `new` | `bank_transfer`, `pending` | реквізити і граничний час оплати |
| `paid` | — | «Оплачено» |
| `shipped` | — | «Відправлено» |
| `delivered` | — | «Доставлено» |
| `cancelled` | — | «Скасовано» |

## Функціональні вимоги (EARS)

| ID | Вимога | Сценарії |
|----|--------|----------|
| REQ-01 | WHEN відвідувач підтверджує замовлення і перевірки V0–V5 пройдено, система SHALL однією атомарною транзакцією створити `order` (`order_status` = `new`, `address_id` адреси з REQ-11, REQ-13, REQ-16 або REQ-23, `ordered_at` = час підтвердження), по одному `order_item` на кожен товар кошика (`quantity` з кошика, `unit_price` = поточна `price`) і `payment` (`pending`, обраний `payment_method`, `payment_amount` = сума `quantity × unit_price`). | S1, S2, S5, S8, S9, S13, S14, S15 |
| REQ-02 | WHEN система виконує транзакцію REQ-01, вона SHALL у цій самій транзакції зменшити `stock_quantity` кожного товару на `quantity` його `order_item`. | S1, S14, S15 |
| REQ-03a | WHEN транзакцію REQ-01 зі способом `cash_on_delivery` завершено, система SHALL показати номер замовлення і суму до сплати. | S1, S5, S9, S13 |
| REQ-03b | WHEN транзакцію REQ-01 зі способом `bank_transfer` завершено, система SHALL показати номер замовлення, суму, реквізити (отримувач, IBAN, ЄДРПОУ, призначення «Замовлення №`order_id`») і граничний час оплати. | S1 |
| REQ-03c | WHEN транзакцію REQ-01 зі способом `card` завершено, система SHALL перенаправити відвідувача на сторінку платіжного шлюзу з `payment_id` і `payment_amount`. | S2 |
| REQ-04 | WHEN шлюз повідомляє про успіх для `payment` зі статусом `pending` або `failed`, `order` якого має статус `new`, система SHALL встановити `payment_status` = `succeeded`, `paid_at` = час платежу, зазначений у повідомленні, і `order_status` = `paid`. | S2 |
| REQ-05 | IF шлюз повідомляє про успіх для `payment` зі статусом `succeeded` або про відмову для `payment`, статус якого не `pending`, THEN система SHALL не змінювати ні `payment`, ні `order`. | S2 |
| REQ-05a | IF повідомлення шлюзу не має дійсного підпису або стосується `payment_id`, якого немає, THEN система SHALL відхилити його, не змінюючи даних, і записати в журнал безпеки. | S16 |
| REQ-06 | WHEN шлюз повідомляє про відмову для `payment` зі статусом `pending`, система SHALL встановити `payment_status` = `failed` і не змінювати `order_status`. | S3 |
| REQ-07 | WHEN відвідувач натискає «Оплатити ще раз», а `order` має статус `new`, останній `payment` — `failed` і до граничного часу ≥ `T_RETRY_MIN`, система SHALL створити новий `payment` (`card`, `pending`, той самий `payment_amount`) і перенаправити відвідувача на сторінку шлюзу. | S3 |
| REQ-08 | WHILE `order` має статус `new` і жоден його `payment` не має статусу `succeeded`, WHEN настає граничний час оплати, система SHALL встановити `order_status` = `cancelled`, `payment` `bank_transfer` зі статусом `pending` — `failed` (картковий `payment` не змінюється), і повернути `quantity` кожного `order_item` у `stock_quantity`. | S4, S10 |
| REQ-08a | WHEN від `ordered_at` минає `T_CARD_FINAL`, а `payment` `card` має статус `pending`, система SHALL встановити йому `failed`. | — |
| REQ-09 | IF (V5) `quantity` хоча б одного товару в кошику більша за його `stock_quantity`, THEN система SHALL не створювати замовлення і показати для кожного такого товару доступну кількість. | S7, S15 |
| REQ-10 | IF (V4) `price` хоча б одного товару відрізняється від ціни, переданої з кошика, THEN система SHALL не створювати замовлення, показати нові ціни й нову суму та оновити ціни в кошику. | S8 |
| REQ-11 | WHILE відвідувач увійшов як клієнт, WHEN він переходить до оформлення, система SHALL показати `address` цього `customer` з можливістю вибрати одну або додати нову. | S1, S2, S13, S14 |
| REQ-12 | WHILE відвідувач не увійшов в акаунт, WHEN він переходить до оформлення, система SHALL показати форму з полями `first_name`, `last_name`, `email`, `phone`, `country`, `city`, `street_line`, `postal_code`, де всі, крім `phone`, позначені як обов'язкові. | S5, S6, S9, S12 |
| REQ-13 | WHEN гість, нормалізований email якого не збігається з email жодного `customer`, підтверджує замовлення, система SHALL у транзакції REQ-01 створити гостьовий запис `customer` (нормалізований `email`, `registered_at` = час підтвердження) і його `address`. | S5 |
| REQ-14 | IF (V2) нормалізований email, введений гостем, належить `customer`, для якого є акаунт, THEN система SHALL не створювати замовлення, показати пропозицію увійти і не змінювати кошик. | S6 |
| REQ-15 | IF (V1) значення поля форми не відповідає «Правилам полів», THEN система SHALL показати помилку біля цього поля, не створювати замовлення і зберегти значення інших полів. | S12 |
| REQ-16 | WHEN гість, нормалізований email якого збігається з email гостьового запису без акаунта, підтверджує замовлення, система SHALL у транзакції REQ-01 створити нову `address` цього `customer`, не створюючи нового `customer` і не змінюючи `first_name`, `last_name`, `phone`, `registered_at`. | S9 |
| REQ-16a | WHILE відвідувач не увійшов в акаунт, система SHALL показувати на сторінках UC5 лише дані поточного замовлення. | S9 |
| REQ-16b | WHEN транзакцію REQ-01 за REQ-16 завершено, система SHALL повідомити гостю, що замовлення оформлено на ім'я, вказане під час першої покупки з цим email, не показуючи самого імені. | S9 |
| REQ-17 | WHEN шлюз повідомляє про успіх для `payment` зі статусом `pending` або `failed`, `order` якого має статус `cancelled` або `paid`, система SHALL встановити `payment_status` = `succeeded` і `paid_at` = час платежу, зазначений у повідомленні, не змінюючи `order_status` і `stock_quantity`. | S10 |
| REQ-18 | IF (V3) сума `quantity × price` усіх товарів кошика дорівнює 0.00, THEN система SHALL не створювати замовлення і показати, що замовлення має містити хоча б один платний товар. | S11 |
| REQ-19 | IF підтвердження надходить з ідентифікатором оформлення, за яким протягом останніх `T_DEDUP` уже створено `order`, THEN система SHALL не створювати нових `order` і `payment`, не змінювати `stock_quantity` і показати номер створеного замовлення. | S14 |
| REQ-20 | WHEN відвідувач відкриває сторінку замовлення, зокрема повертаючись зі шлюзу, система SHALL показати стан за таблицею «Стани сторінки замовлення». | S2, S3 |
| REQ-20a | WHILE сторінка замовлення відкрита у стані «Оплата обробляється», система SHALL оновлювати її кожні `T_REFRESH`. | S2 |
| REQ-21 | WHEN транзакцію REQ-01 завершено, система SHALL очистити кошик у браузері відвідувача. | S1, S2, S5 |
| REQ-22 | IF відвідувач натискає «Оплатити ще раз», а умови REQ-07 не виконано, THEN система SHALL не створювати `payment` і показати сторінку замовлення в поточному стані. | S10 |
| REQ-23 | WHEN клієнт додає нову адресу й підтверджує замовлення, система SHALL у транзакції REQ-01 створити `address` з `customer_id` цього клієнта, не змінюючи інших його адрес. | S13 |
| REQ-24 | Система SHALL обробляти повідомлення шлюзу (REQ-04–REQ-06, REQ-17) і переходи за часом (REQ-08, REQ-08a) для одного `order` послідовно, по одному. | S10 |
| REQ-25 | IF підтвердження не проходить кілька перевірок V0–V5, THEN система SHALL показати повідомлення лише першої непройденої за порядком V0→V5. | — |
| REQ-26 | IF (V0) кошик порожній, містить `quantity`, що не є цілим числом ≥ 1, або `product_id`, якого немає в каталозі, THEN система SHALL не створювати замовлення, показати «Кошик змінився» і прибрати з кошика недійсні рядки. | S17 |

## Нефункціональні вимоги (NFR)

NFR не наносяться на діаграму й не трасуються. Час відгуку міряється на сервері: від отримання запиту до відправлення відповіді.

| ID | Категорія | Вимога | Як перевірити (пройдено, якщо…) |
|----|-----------|--------|----------------------------------|
| NFR-01 | Продуктивність | За пікового навантаження 20 підтверджень/с протягом 10 хв (звичайне — до 300 замовлень/год) і каталогу 10 000 товарів час відповіді на підтвердження: p95 ≤ 2 с, p99 ≤ 4 с. | навантажувальний тест, ≥ 12 000 вимірювань із ≥ 150 IP-адрес, щоб не перевищити NFR-09: обидві межі дотримано |
| NFR-02 | Цілісність | Коли 50 відвідувачів одночасно підтверджують по 1 шт. товару з `stock_quantity` = 10, створюється рівно 10 замовлень, решта 40 отримують відмову за REQ-09, `stock_quantity` = 0. | 100 прогонів: усі дали рівно 10 замовлень і жодного від'ємного залишку |
| NFR-03 | Своєчасність | Повідомлення шлюзу фіксується в `payment` за p95 ≤ 3 с і не довше ніж за 10 с від отримання запиту шлюзу. | 1 000 повідомлень від підставного шлюзу: обидві межі дотримано |
| NFR-04 | Своєчасність | Перехід за REQ-08 і REQ-08a відбувається не пізніше ніж через 60 с після настання строку. | 200 замовлень зі зсунутим годинником: 100 % у межі |
| NFR-05 | Доступність сервісу | Оформлення доступне ≥ 99,5 % хвилин календарного місяця (простій ≤ 216 хв за 30 днів). Простій — хвилина, у якій зовнішня перевірка отримала не 2xx або чекала довше 10 с; планові роботи входять у цей бюджет і проводяться лише 01:00–05:00 за Києвом. | моніторинг щохвилини за місяць |
| NFR-06 | Безпека | Номер картки й CVV не надходять у систему: їх вводять лише на сторінці шлюзу. | у схемі БД немає полів для них; пошук шаблону номера картки в логах за 7 днів тестів — 0 збігів |
| NFR-07 | Безпека | Увесь трафік — лише HTTPS з TLS ≥ 1.2; HTTP-запит отримує перенаправлення 301 на HTTPS. | сканування конфігурації TLS: жодної версії нижче 1.2 |
| NFR-08 | Безпека | Повідомлення шлюзу приймаються лише з дійсним підписом HMAC-SHA256; відхилені записуються в журнал безпеки, який зберігається 90 днів. | 100 підроблених повідомлень: 0 змін даних, 100 записів у журналі |

| NFR-10 | Пристрої | Chrome, Edge, Firefox, Safari — дві останні мажорні версії станом на 01.11.2026; Android ≥ 11, iOS ≥ 16; ширина екрана від 360 px без горизонтальної прокрутки на всіх сторінках UC5. | ручний прогін S1, S2, S5, S12, S13 на кожній платформі: 0 дефектів відображення |

Технічні дані (сесії, ідентифікатори оформлення, облікові дані, журнал безпеки) і реквізити магазину — поза доменними таблицями. | у схемі рівно 9 доменних таблиць, поля й типи збігаються з `lab1/spec.md`; вставка email, що відрізняється лише регістром, відхиляється |

## Поза обсягом

| Що не робимо | Чому |
|--------------|------|
| Кошик як дані на сервері (UC3) | у моделі lab1 немає сутності кошика; кошик зберігає інтерфейс у браузері (частина системи) і передає його вміст разом із підтвердженням. |
| Вхід, паролі, відновлення доступу | у `customer` немає облікових даних; автентифікація — окрема підсистема, для UC5 вхід — передумова. |
| Обробка, відвантаження й доставка (статуси `shipped`, `delivered`, UC12) | це наступний прецедент Менеджера; служба доставки в цій роботі нічого не ініціює. |
| Повернення коштів (статус `refunded`) | окремий процес з менеджером і шлюзом. Після REQ-17 у даних лишається ознака: `order` `cancelled` або `paid` має `payment` `succeeded` понад потрібний — за нею такі замовлення знаходить UC12. |
| Підтвердження банківського переказу й оплати при отриманні | виконує Менеджер в UC12; тому для `cash_on_delivery` у UC5 немає граничного часу. |
| Знижки, промокоди, доставка за гроші | у моделі немає полів для них; `payment_amount` = сума позицій. |
| Замовлення лише з безкоштовних товарів | `payment_amount` > 0 у моделі lab1, а замовлення без `payment` не має способу оплати; безкоштовний товар можна замовити лише разом із платним (REQ-18). |
| Кілька валют, мов і країн доставки | магазин працює в Україні (NFR-11, NFR-12, правило `country`). |
| Часткова оплата | сума замовлення не ділиться на кілька `payment`; повтор — лише після `failed` (REQ-07). Якщо шлюз підтвердив два списання (пізній успіх за `failed` і успіх нового `payment`), обидва записуються як `succeeded` (REQ-04, REQ-17), а зайве повертає UC12. |
| Повернення гостя до неоплаченого замовлення після закриття сторінки | гість не має UC9; повторити оплату він може лише зі сторінки замовлення (REQ-07, REQ-20); посилання в листі — частина сповіщень. |
| Скасування замовлення клієнтом або менеджером | окремий прецедент; в UC5 скасування відбувається лише за часом (REQ-08). |
| Видалення адрес і відгуки (UC8, UC10) | не належать до UC5; адресу з замовленнями змінювати не можна (lab1, ADR 0002). |
| Окремий одержувач замовлення | у моделі lab1 ім'я є лише в `customer`, а не в `address` чи `order`; одержувач — завжди сам `customer` (тому REQ-16 не перезаписує ім'я). |
| Товар, який прибрали з каталогу, поки він у кошику | у моделі немає ознаки «знято з продажу»; керування каталогом — UC11. |
| Причина відмови платежу | у `payment` немає поля причини; відмова банку, неоплата переказу й `T_CARD_FINAL` однаково дають `failed`. |
| Окрема адресна книга | у lab1 адреса доставки й збережена адреса — одна сутність `address`, тому кожна вказана адреса стає збереженою (REQ-11 її показує), а змінювати її не можна (ADR 0002 lab1). |
