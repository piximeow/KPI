# Специфікація: вимоги до UC5 «Оформити замовлення»

**Намір.** Розписати вглиб один складний прецедент онлайн-магазину: UC-діаграма → сценарії Gherkin (вони ж user stories) → EARS під них → NFR → трасування. Дані — з моделі lab1, модель не змінюється. Артефакти: `use-cases.md`, `diagrams/`, `features/`, `requirements.md`, `traceability.md`.

## Актори та цілі

| Актор | Мета |
|-------|------|
| Відвідувач (абстрактний) | знайти й купити товар |
| Гість ← Відвідувач | купити без акаунта або створити акаунт |
| Клієнт ← Відвідувач | купувати зі збереженими адресами, бачити свої замовлення, оцінювати товари |
| Менеджер магазину | вести каталог, доводити замовлення до доставки |
| Платіжний шлюз (другорядний, UC7) | повідомити результат оплати карткою (сам ініціює) |

**Терміни.** *Система* — увесь веб-застосунок разом з інтерфейсом у браузері. *Акаунт* — облікові дані для `customer_id` у підсистемі входу (поза моделлю). *Гостьовий запис* — `customer` без акаунта, створений UC5 для гостя. `registered_at` — час створення запису `customer`, гостьового теж.

## Кроки UC5

1. Відвідувач із непорожнім кошиком переходить до оформлення.
2. Вибирає або вказує адресу (UC6).
3. Обирає `cash_on_delivery`, `bank_transfer` або `card` (UC7).
4. Підтверджує; система перевіряє кошик, поля, email, суму, ціну, залишок і створює `order`, `order_item`, `payment`, відкладаючи товар.
5. Для картки шлюз повідомляє результат; неоплачене замовлення скасовується в граничний час оплати.

## Критерії прийняття

- [ ] 1. 5 акторів, 12 UC; Гість і Клієнт успадковують абстрактного Відвідувача; є `include` і `extend`; жоден UC не є дією системи. `include` виконується щоразу; точка розширення — місце в потоці базового UC; умова `extend` не ширша за вимоги.
- [ ] 2. Зовнішня система — актор, лише якщо сама ініціює взаємодію.
- [ ] 3. UC5 має ≥ 3 сценарії Gherkin, з них ≥ 2 помилкові; розділу «User stories» немає.
- [ ] 4. Кожна EARS — один шаблон (WHEN — подія, WHILE — стан, IF…THEN — небажана ситуація, без слова — завжди), один тригер, одна реакція (атомарна транзакція — одна реакція); показ в інтерфейсі — через стан сторінки; кожна константа визначена в одному місці.
- [ ] 5. Кожна NFR — одна вимога з числом, межею, умовами виміру й критерієм «пройдено/ні»; NFR немає на діаграмі й у матриці.
- [ ] 6. Сутності, поля й статуси існують у моделі lab1 і вживаються за змістом; жодна вимога не створює запис, що порушує її обмеження чи кардинальності; NFR не суперечать правилам моделі (зокрема M:N L3); тестові дані — допустимі записи.
- [ ] 7. Матриця багато-до-багатьох; кожен сценарій має ≥ 1 вимогу; непокрите — з обґрунтуванням.
- [ ] 8. Кожен пункт «Поза обсягом» має причину.
- [ ] 9. Однакові величини збігаються в сценаріях, EARS і NFR.
- [ ] 10. `spec.md` і `DEFENSE.md` — не більше сторінки кожен.
- [ ] 11. Гостьовий email: новий → новий `customer`; є гостьовий запис → він же; є акаунт → пропозиція увійти. Один email — один `customer`.
- [ ] 12. Реакцію на повідомлення шлюзу визначено для кожного статусу `order` і `payment`; підтверджене шлюзом списання завжди записується як `succeeded`.
- [ ] 13. Кожен кінець UC5 має сценарій; «Передумова» містить лише спільні дані й не суперечить жодному сценарію.
