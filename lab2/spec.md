# Специфікація: вимоги до UC5 «Оформити замовлення»

**Намір.** Розписати вглиб один складний прецедент онлайн-магазину: UC-діаграма → сценарії Gherkin (вони ж user stories) → EARS під них → NFR → трасування. Дані — з моделі lab1, модель не змінюється. Артефакти: `use-cases.md`, `diagrams/`, `features/`, `requirements.md`, `traceability.md`.

## Актори та цілі

| Актор | Мета |
|-------|------|
| Відвідувач (абстрактний) | знайти й купити товар |
| Гість ← Відвідувач | купити без акаунта або створити акаунт |
| Клієнт ← Відвідувач | купувати зі збереженими адресами, бачити свої замовлення, оцінювати товари |
| Менеджер магазину | вести каталог, доводити замовлення до доставки |
| Платіжний шлюз (другорядний, UC7) | повідомити результат оплати карткою (сам ініціює) |

**Терміни.** *Система* — увесь веб-застосунок разом з інтерфейсом у браузері. *Акаунт* — облікові дані для `customer_id` у підсистемі входу (поза моделлю). *Гостьовий запис* — `customer` без акаунта, створений UC5 для гостя. `registered_at` — час створення запису `customer`, гостьового теж.

## Кроки UC5

1. Відвідувач із непорожнім кошиком переходить до оформлення.
2. Вибирає або вказує адресу (UC6).
3. Обирає `cash_on_delivery`, `bank_transfer` або `card` (UC7).
4. Підтверджує; система перевіряє кошик, поля, email, суму, ціну, залишок і створює `order`, `order_item`, `payment`, відкладаючи товар.
5. Для картки шлюз повідомляє результат; неоплачене замовлення скасовується в граничний час оплати.

## Критерії прийняття

- [x] 1. 5 акторів, 12 UC; Гість і Клієнт успадковують абстрактного Відвідувача; є `include` і `extend`; жоден UC не є дією системи. `include` виконується щоразу; точка розширення — місце в потоці базового UC; умова `extend` не ширша за вимоги.
- [x] 2. Зовнішня система — актор, лише якщо сама ініціює взаємодію.
- [x] 3. UC5 має ≥ 3 сценарії Gherkin, з них ≥ 2 помилкові; розділу «User stories» немає.
- [x] 4. Кожна EARS — один шаблон EARS (простий або складений WHILE…WHEN: стан + подія), одна умова, одна реакція (кілька змін даних — лише як одна атомарна транзакція, названа у вимозі); показ в інтерфейсі — через стан сторінки; кожна константа й припущення визначені в одному місці.
- [x] 5. Кожна NFR — одна вимога з числом, межею, умовами виміру й критерієм «пройдено/ні»; NFR немає на діаграмі й у матриці.
- [x] 6. Сутності, поля й статуси існують у моделі lab1 і вживаються за змістом; жодна вимога не створює запис, що порушує її обмеження чи кардинальності; NFR не суперечать правилам моделі (зокрема M:N L3); тестові дані — допустимі записи.
- [x] 7. Матриця багато-до-багатьох; кожен сценарій має ≥ 1 вимогу; непокрите — з обґрунтуванням.
- [x] 8. Кожен пункт «Поза обсягом» має причину.
- [x] 9. Однакові величини й формати (суми на екрані — за NFR-12) збігаються в сценаріях, EARS і NFR.
- [x] 10. `spec.md` і `DEFENSE.md` — не більше сторінки кожен.
- [x] 11. Гостьовий email: новий → новий `customer`; є гостьовий запис → він же; є акаунт → пропозиція увійти. Один email — один `customer`.
- [x] 12. Реакцію на повідомлення шлюзу (успіх, відмова) визначено для кожного з 5 статусів `order` і 4 статусів `payment`; підтверджене шлюзом списання завжди записується як `succeeded`, крім уже `succeeded` чи `refunded`; дубль підтвердження відвідувача перевіряється раніше за всі перевірки V0–V5.
- [x] 13. Кожен кінець UC5 має сценарій; «Передумова» містить лише спільні дані й не суперечить жодному сценарію.
- [x] 14. Кожен сценарій перевіряє одну поведінку: одна дія «Коли» і її результат «Тоді»; кожна EARS має щонайменше один сценарій.
