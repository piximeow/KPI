# Специфікація: вимоги до UC5 «Оформити замовлення»

**Намір.** Описати вимоги до одного складного прецедента онлайн-магазину вглиб: UC-діаграма → сценарії в Gherkin (вони ж user stories) → EARS під ці сценарії → NFR → трасування. Дані беруться з моделі lab1 (`../lab1/model.md`), модель не змінюється.

## Актори та цілі

| Актор | Мета |
|-------|------|
| Відвідувач (узагальнений) | знайти й купити товар |
| Гість ← Відвідувач | купити без акаунта або створити акаунт |
| Клієнт ← Відвідувач | купувати зі збереженими адресами, бачити свої замовлення, оцінювати товари |
| Менеджер магазину | вести каталог, доводити замовлення до доставки |
| Платіжний шлюз | повідомити результат оплати карткою (сам ініціює) |

Повний перелік UC і зв'язків: `use-cases.md`.

**Терміни.** *Акаунт* — облікові дані в підсистемі входу (поза моделлю lab1) для `customer`. *Гостьовий запис* — `customer` без акаунта, який створює UC5 для гостя. `registered_at` — час створення запису `customer`, гостьового теж.

## Кроки UC5 (основний потік)

1. Відвідувач із непорожнім кошиком переходить до оформлення.
2. Вказує адресу (UC6): клієнт обирає збережену, гість вводить контакти й адресу.
3. Обирає спосіб оплати: `cash_on_delivery`, `bank_transfer` або `card` (UC7).
4. Підтверджує; система перевіряє залишок і ціну, створює `order`, `order_item`, `payment`, відкладає товар.
5. Для картки — шлюз повідомляє результат; неоплачене замовлення скасовується в граничний час оплати (константи — `requirements.md`), а результат картки приймається й після цього.

## Критерії прийняття

- [ ] 1. На діаграмі 5 акторів і 12 UC; є узагальнення Гість/Клієнт → Відвідувач, щонайменше один `include` і один `extend` з умовою; жоден UC не є дією системи.
- [ ] 2. Зовнішня система є актором лише тоді, коли сама ініціює взаємодію (тільки Платіжний шлюз).
- [ ] 3. UC5 має щонайменше 3 сценарії в Gherkin, з них щонайменше 2 помилкові; розділу «User stories» немає.
- [ ] 4. Кожна функціональна вимога записана за одним шаблоном EARS (WHEN — подія, WHILE — стан, IF…THEN — небажана ситуація, без ключового слова — завжди) з одним тригером і однією реакцією (атомарна транзакція — одна реакція); показ в інтерфейсі описується станом сторінки, а не реакцією на серверну подію; кожна константа (терміни, ліміти) визначена в одному місці.
- [ ] 5. Кожна NFR — одна вимога з числом, межею, умовами виміру й критерієм «пройдено/ні»; NFR немає ні на діаграмі, ні в матриці.
- [ ] 6. Усі сутності, поля й значення статусів у сценаріях і вимогах існують у моделі lab1, і жодна вимога не може створити запис, що порушує її обмеження (діапазони, обов'язковість, унікальність).
- [ ] 7. Матриця трасування багато-до-багатьох; кожен сценарій має ≥ 1 вимогу, кожна непокрита вимога чи UC має обґрунтування.
- [ ] 8. Кожен пункт «Поза обсягом» має причину.
- [ ] 9. Однакові величини (терміни оплати, суми, статуси) збігаються в сценаріях, EARS і NFR.
- [ ] 10. `spec.md` і `DEFENSE.md` — кожен не більше однієї сторінки.
- [ ] 11. Для кожного гостьового email визначено результат: новий → створюється `customer`; є гостьовий запис → використовується він; є акаунт → пропозиція увійти. Одному email відповідає рівно один `customer`.
- [ ] 12. Реакцію на повідомлення шлюзу визначено для кожного поточного статусу `order` (`new`, `paid`, `cancelled`) і `payment`; списання, яке підтвердив шлюз, завжди записується як `succeeded`, навіть для скасованого замовлення.
- [ ] 13. Кожен кінець UC5 з `use-cases.md` (успіх і кожен вид невдачі) має щонайменше один сценарій; «Передумова» містить лише дані, спільні для всіх сценаріїв, і жоден сценарій їй не суперечить.
