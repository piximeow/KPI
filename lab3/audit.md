# Аудит sequence-діаграм

Відповіді й рішення за кожною знахідкою — `ai/prompts.md` (П1, П2). Кожне виправлення з топ-3 спершу змінювало критерій у spec, потім діаграми; розділ spec «Кроки сценаріїв» синхронізовано з діаграмами після них.

## 1. Учасники ↔ ER-модель lab1
Сутності-учасники мають імена lab1 (`address`, `product`, `order`, `order_item`, `payment`); Клієнт — `customer`. Усі поля, ключі, статуси й способи оплати в діаграмах звірила з `lab1/spec.md` вручну — збігаються. Поза моделлю лише сервіси, UI й таймер (spec, «Учасники»). Виправлено: `orderId` → `order_id`, позиційні аргументи → `поле = значення`, `findByOrder` без ключа. Межі сервісів — `adr/0001`.

## 2. Кроки ↔ сценарії Gherkin і вимоги lab2
Виправлено: S03 без гілки «12:16:00», S04 без `decreaseStock` у відкаті, S02 зі створенням у `Note`, злиті рядки «Приклади», гілки поза сценарієм (S01 `card`, S05 `pending`), `paid_at` після очікування блокування, неповні шапки. Кроки інтерфейсу поза lab2 (`disableConfirm()`) позначено в шапках.

## 3. Техніка
Один return на виклик, `commit()`/`rollback()` у кожній транзакції, дії Клієнта з відповіддю інтерфейсу, асинхронний таймер, спостереження — у `Note`. Усі 5 діаграм рендеряться `mmdc`.

## 4. Що діаграми показали про lab2 (вимоги не змінюю)
- Повторне підтвердження після загубленої відповіді або з двох вкладок створить другий `order`: примітка REQ-08 / REQ-17 розрахована на кошик на сервері.
- Успіх від шлюзу після скасування: гроші списано, `order` `cancelled`, `refunded` ніхто не ставить.
- REQ-11, REQ-12, REQ-15 не обмежені `card`.
- Після оплати карткою Клієнт не бачить результату (UC5 поза обсягом).
- Немає перевірки `quantity ≥ 1` у кошику з браузера: від'ємна сума пройде REQ-09, і замовлення відхилить лише обмеження `payment_amount > 0` у БД через REQ-06 з неточним повідомленням.
- У `payment` немає часу створення — таймер відлічує від `ordered_at` (`adr/0002`).
- Лічильник REQ-20 поза транзакцією: два одночасні підтвердження можуть дати 101-й `order`.
