# Аудит sequence-діаграм

Відповіді чату й рішення за кожною знахідкою — `ai/prompts.md` (П1, П2). Кожне виправлення з топ-3 спершу змінювало критерій у spec, потім діаграми; розділ spec «Кроки сценаріїв» синхронізовано з діаграмами після них.

## 1. Учасники ↔ ER-модель lab1
Сутності-учасники мають імена lab1 (`address`, `product`, `order`, `order_item`, `payment`); Клієнт — `customer`. Усі поля, ключі, статуси й способи оплати в діаграмах звірила з `lab1/spec.md` вручну — збігаються. Поза моделлю лише сервіси, UI й таймер (spec, «Учасники»). Виправлено: `orderId` → `order_id`, позиційні аргументи → `поле = значення`, `findByOrder` без ключа. Межі сервісів — `adr/0001`.

## 2. Кроки ↔ сценарії Gherkin і вимоги lab2
Виправлено: S03 без гілки «12:16:00», S04 без `decreaseStock` у відкаті, S02 зі створенням у `Note`, злиті рядки «Приклади», гілки поза сценарієм (S01 `card`, S05 `pending`), `paid_at` після очікування блокування, неповні шапки. Кроки поза lab2 (`disableConfirm()`) позначено в шапках.

## 3. Техніка
Один return на виклик, `commit()`/`rollback()` у кожній транзакції, дії Клієнта з відповіддю інтерфейсу, асинхронний таймер, спостереження — у `Note`. Усі 5 діаграм рендеряться `mmdc`.

## 4. Що діаграми показали про lab2 (вимоги не змінюю)
Для кожної прогалини — наслідок щодо моделі lab1 (критерій 12).
- **Повторне підтвердження** після загубленої відповіді або з двох вкладок: другий `order`. Модель не порушено, але стан неправдивий. Примітка REQ-08 / REQ-17 розрахована на кошик на сервері, а він у браузері.
- **Успіх від шлюзу після скасування**: гроші списано, `order` `cancelled`, `payment` `failed`. У межах моделі, але неправдиво: `refunded` ніхто не ставить.
- **REQ-11, REQ-12, REQ-15 не обмежені `card`**: підписане повідомлення для `payment` `cash_on_delivery` у `pending` переведе його в `succeeded`. Стан дозволений моделлю, але неправдивий.
- **Після оплати карткою Клієнт не бачить результату в магазині** (UC5 поза обсягом). Даних не стосується.
- **Кошик з браузера без перевірки `quantity ≥ 1`**: від'ємна `quantity` дає від'ємну суму, REQ-09 її не ловить, і вимоги lab2 дозволяють `order_item` з `quantity < 1`, який модель lab1 забороняє. Якщо БД перевіряє обмеження, спрацює REQ-06 з неточним повідомленням. Сам ризик lab2 уже записала (`requirements.md`, «Обмеження моделі»; `spec.md`, «Поза обсягом» п. 6), діаграми показують його наслідок.
- **У `payment` немає часу створення**: lab2 уже відлічує REQ-13 від `ordered_at` («Обмеження моделі»), діаграми лише показують, що таймер ставиться в тій самій транзакції (`adr/0002`). У межах моделі.
- **Лічильник REQ-20 поза транзакцією**: два одночасні підтвердження можуть дати 101-й `order`. Модель не порушено, ліміт неточний.
