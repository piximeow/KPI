# Специфікація: sequence-діаграми UC2 «Оформити замовлення»

## Намір
Для кожного з 5 сценаріїв UC2 (lab2) показати sequence-діаграмою Mermaid, хто кого викликає, у якому порядку й що змінюється в даних. Модель lab1 і вимоги lab2 не змінюю.

## Прецедент і сценарії
UC2 «Оформити замовлення» (Клієнт; розширення UC4 «Оплатити карткою» з Платіжним шлюзом). Сценарії — `lab2/features/uc2-place-order.feature`.

## Учасники
| Учасник | Тип | Відповідальність / звідки в моделі |
|---|---|---|
| Клієнт, Платіжний шлюз | actor | актори lab2; Клієнт — `customer` |
| `CheckoutUI` | інтерфейс у браузері | форма, кошик, показ повідомлень і номера `order` |
| `CheckoutService` | сервіс | перевірки відмов, створення `order`, `order_item`, `payment`, зменшення `stock_quantity`, постановка таймера |
| `PaymentService` | сервіс | повідомлення шлюзу й таймера: статуси `payment` і `order`, повернення `stock_quantity` |
| `PaymentTimer` | таймер | через 15 хв після створення `payment` з `card` викликає `PaymentService` |
| `address`, `product`, `order`, `order_item`, `payment` | сутності lab1 | таблиці; `critical` — транзакція |

## Кроки сценаріїв
- **S01** оплата при отриманні: «Оформити» → форма з адресами → «Підтвердити» → перевірки ліміту й форми → `critical` { блокування товарів, перевірка залишку й суми, `order`, `loop` `order_item` + зменшення залишку, `payment` } → очистити кошик → `alt` за способом: показати `order_id`.
- **S02** картка: як S01 з `card` → таймер 15 хв → redirect на шлюз → повідомлення шлюзу → перевірка підпису → `critical` { `payment` під блокуванням, `alt` `pending` → `succeeded` і `paid` }.
- **S03** шлюз або таймер: `alt` за подією: відмова банку / 12:14:59 / таймер / успіх і слідом таймер; скасування — `failed`, `cancelled`, `loop` повернення залишку.
- **S04** відмова: `alt` «Оформити» без адрес / «Підтвердити»: `alt` у порядку REQ-22 — ліміт, форма, порожній кошик, `critical` { брак товару, сума 0, збій і відкат }.
- **S05** повідомлення без змін: перевірка підпису → `alt` недійсний / дійсний → `critical` { `payment` не `pending` → нічого не змінюється }.

## Критерії прийняття
1. 5 діаграм, по одній на сценарій S1–S5; кожен рядок «Приклади» — гілка `alt` або `Note`.
2. У кожній діаграмі є `alt`, `opt` або `loop`; транзакція й обробка «по одному» — `critical`.
3. Учасники — лише з таблиці; сутності мають імена lab1; кожен учасник бере участь у виклику.
4. Синхронний виклик (`->>`) має return (`-->>`); redirect і постановка таймера — асинхронні (`-)`).
5. Активація починається з викликом і закінчується return того самого виклику.
6. Кроки відповідають «Коли»/«Тоді» сценарію та його вимогам lab2; «Дано» — `Note`.
7. Дані змінює лише сервіс, відповідальний за них у таблиці.
8. Кожна діаграма — текст Mermaid і SVG з того самого тексту.
9. `spec.md` і `DEFENSE.md` — до сторінки кожен.
