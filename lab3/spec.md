# Специфікація: sequence-діаграми UC2 «Оформити замовлення»

## Намір
Для кожного з 5 сценаріїв UC2 «Оформити замовлення» (Клієнт; розширення UC4 з Платіжним шлюзом; `lab2/features/uc2-place-order.feature`) показати sequence-діаграмою, хто кого викликає й що змінюється в даних. Модель lab1 і вимоги lab2 не змінюю.

## Учасники
| Учасник | Відповідальність / звідки в моделі |
|---|---|
| Клієнт, Платіжний шлюз | актори lab2; Клієнт — `customer` |
| `CheckoutUI` | форма, кошик (у браузері, lab2 «Поза обсягом» п. 6); блокує «Підтвердити» до відповіді |
| `CheckoutService` | усе до й під час створення: перевірки відмов, `order`, `order_item`, `payment`, зменшення `stock_quantity`, постановка таймера |
| `PaymentService` | усе після створення: повідомлення шлюзу й таймера, статуси `payment` і `order`, повернення `stock_quantity` |
| `PaymentTimer` | через 15 хв від `ordered_at` викликає `PaymentService` |
| `address`, `product`, `order`, `order_item`, `payment` | сутності lab1; `critical` — транзакція до `commit()` або `rollback()` |

## Кроки сценаріїв
- **S01** «Оформити» → адреси цього customer → «Підтвердити» → ліміт і форма → `critical` { блокування, залишок і сума, `order`, `loop` { `order_item`, −залишок }, `payment` } → очистити кошик → `order_id`.
- **S02** як S01 з `card` + таймер у транзакції → перенаправлення на шлюз → повідомлення з дійсним підписом → `critical` { `succeeded`, `paid` }.
- **S03** `alt`: відмова банку / 12:14:59 / таймер до 12:16:00 / успіх і слідом таймер; скасування — `failed`, `cancelled`, `loop` +залишок.
- **S04** `alt`: «Оформити» без адрес / відмови в порядку REQ-22, у `critical` — брак товару, сума 0, збій і `rollback`.
- **S05** підпис → `alt` недійсний / дійсний: `payment` не `pending` → без змін.

## Критерії прийняття
1. По діаграмі на сценарій S1–S5; кожен рядок «Приклади» — гілка `alt` або `Note` з номером, у порядку перевірок системи (сказано в `Note`); гілок поза сценарієм немає.
2. У кожній діаграмі є `alt`, `opt` або `loop`; транзакція й обробка «по одному» — `critical`.
3. Учасники — лише з таблиці, імена полів і ключів — як у lab1; кожен учасник бере участь у виклику.
4. Синхронний виклик має return (дія Клієнта — відповідь UI; шлюзу — `Accepted`/`Rejected`); таймер — асинхронний; самовиклик — без return.
5. Активація закінчується єдиним return свого виклику (таймер — `deactivate`); у гілках результат лише готується; спостереження — у `Note`.
6. Кроки — у порядку й часі «Коли»/«Тоді» сценарію та його вимог; «Дано» і зміни поза UC2 — `Note`, зміни UC2 — викликами. У шапці — вимоги сценарію і «також».
7. Дані змінює лише відповідальний сервіс; зміни поза UC2 — лише `Note`.
8. Кожна діаграма — текст Mermaid і SVG з того самого тексту.
9. `spec.md` і `DEFENSE.md` — до сторінки кожен.
10. У записах (`insert…`, `update…`, `decreaseStock`, `increaseStock`) ключі `*_id` — назвою поля, решта — `поле = значення`; параметри запитів — без цього правила.
11. У шапці — кроки поза lab2 і «також» (згадані вимоги понад сценарій).
12. Розбіжність lab2 в аудиті має наслідок щодо моделі lab1.
