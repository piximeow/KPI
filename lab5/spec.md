# Специфікація: компонентна модель онлайн-магазину (UC2 + UC4)

## Намір
Показати архітектуру, що реалізує UC2 «Оформити замовлення» з UC4 «Оплатити карткою»: компоненти, provided/required-інтерфейси, залежності, межу системи й зовнішні інтеграції. Сервіси, UI і таймер — учасники lab3 (у lab4 — доріжки «Клієнт (CheckoutUI)» і «Магазин»); дані — модель lab1. Нові в lab5 лише `CheckoutAPI` і `PaymentWebhook` — HTTP-вхід у систему без власної логіки (`adr/0001`).

## Модулі
| Шар | Компонент | Відповідає |
|---|---|---|
| UI | `CheckoutUI` (браузер) | форма, кошик, повідомлення, перехід на шлюз (REQ-01, 02, 10, 17, 18) |
| API | `CheckoutAPI` | HTTP-вхід UI: `openCheckout`, `confirmOrder` |
| API | `PaymentWebhook` | HTTP-вхід шлюзу: `notifyPayment` → `Accepted`/`Rejected` |
| Сервіси | `CheckoutService` | адреси (UC3), перевірки REQ-22, транзакція створення, постановка таймера (REQ-03–09, 13, 19, 20) |
| Сервіси | `PaymentTimer` | спрацювання через 15 хв від `ordered_at` (REQ-13) |
| Сервіси | `PaymentService` | підпис, події по одному, статуси, повернення залишку (REQ-11–16, 21) |
| Data Access | `AddressRepository`, `ProductRepository`, `OrderRepository` (`order`, `order_item`), `PaymentRepository` | операції з сутностями lab1 з sequence lab3 |
| БД | `ShopDB` | таблиці lab1, що беруть участь в UC2 |

## Зовнішні інтеграції й межа системи
- Усередині — усі компоненти вище. Зовні — Клієнт і Платіжний шлюз; межу перетинають лише інтерфейси: сторінки `CheckoutUI` (для Клієнта), `ICheckout` і `IPaymentNotify` (API), сторінка оплати шлюзу. Обмін — лише HTTPS (NFR-05).
- **Платіжний шлюз** надає сторінку оплати (дані картки вводять лише там — NFR-05) і надсилає `notifyPayment` з підписом HMAC-SHA256.
- Поза моделлю: вхід Клієнта (облікових даних у lab1 немає), UC5 (статус замовлення), email/SMS (вимог немає).

## Критерії прийняття
1. UML Component Diagram у PlantUML; текст і SVG з того самого тексту.
2. Кожен компонент має provided-інтерфейс; кожна залежність — usage-стрілка до provided-інтерфейсу іншого компонента; операції інтерфейсів — ті самі, що в lab3.
3. Межа системи — рамка; зовнішні учасники й інтеграції — поза нею, зі своїми інтерфейсами.
4. Кожен компонент і залежність трасується до lab1–lab4 (таблиця в аудиті); нові компоненти названо й обґрунтовано.
5. Шари на діаграмі йдуть згори вниз (UI → API → сервіси → Data Access → БД); залежності — лише вниз або всередині шару сервісів, без циклів.
6. `spec.md` і `DEFENSE.md` — до сторінки кожен.
