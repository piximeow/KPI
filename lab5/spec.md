# Специфікація: компонентна модель онлайн-магазину (UC2 + UC4)

## Намір
Архітектура UC2 «Оформити замовлення» з UC4 «Оплатити карткою». `CheckoutUI`, сервіси й таймер — з lab3 і lab4; дані — lab1. Нові в lab5: `CheckoutAPI` і `PaymentWebhook` — HTTP-вхід сервера без власної логіки (`adr/0001`); репозиторії й `ShopDB` — на місці сутностей lab3, `order` з `order_item` — в одному (`adr/0002`).

## Модулі
| Шар | Компонент | Відповідає |
|---|---|---|
| UI | `CheckoutUI` (браузер) | форма, кошик, повідомлення, перехід на шлюз (REQ-10, 17, 18) |
| API | `CheckoutAPI` | HTTP-вхід UI: `openCheckout`, `confirmOrder` |
| API | `PaymentWebhook` | HTTP-вхід шлюзу: `notifyPayment` |
| Сервіси | `CheckoutService` | адреси (UC3, REQ-01, 02), перевірки REQ-22, транзакція створення, таймер (REQ-03–09, 13, 19, 20) |
| Сервіси | `PaymentTimer` | спрацювання через 15 хв від `ordered_at` (REQ-13) |
| Сервіси | `PaymentService` | підпис, події по одному, статуси, повернення залишку (REQ-11–16, 21); інтерфейси окремо для шлюзу й таймера |
| Data Access | `AddressRepository`, `ProductRepository`, `OrderRepository` (`order`, `order_item`), `PaymentRepository` | операції з сутностями lab1 з lab3 |
| БД | `ShopDB` | таблиці lab1 для UC2, з `customer` як ціллю FK `address.customer_id` |

## Зовнішні інтеграції й межа системи
- Усередині — усі компоненти вище, `CheckoutUI` — у браузері. Зовні — Клієнт і Платіжний шлюз; межу перетинають лише стрілки до інтерфейсів: Клієнт → `IPages`, `CheckoutUI` → `IPaymentPage`, шлюз → `IPaymentNotify`. Обмін — лише HTTPS з TLS ≥ 1.2 (NFR-05).
- **Платіжний шлюз** надає сторінку оплати; номер картки й CVV Клієнт вводить лише там, повз межу магазину (NFR-05). Шлюз надсилає `notifyPayment` з підписом HMAC-SHA256.
- Поза моделлю (наслідки входу й таймерів — в аудиті): вхід Клієнта (у lab1 немає облікових даних), UC5, email/SMS (без вимог), таймери після перезапуску (`lab3/adr/0002`).

## Критерії
1. UML Component Diagram у PlantUML; текст і SVG з того самого тексту.
2. Кожен компонент має provided-інтерфейс; кожна залежність — usage-стрілка до provided-інтерфейсу іншого компонента; операції інтерфейсів — ті самі, що в lab3 (`IPages` — дії Клієнта «Оформити», «Підтвердити»; `IPaymentPage` — дані REQ-10; `SQL` — БД, якої в lab3 немає).
3. Межа системи — рамка; зовнішні учасники — поза нею, зі своїми інтерфейсами; дані картки — лише Клієнт → шлюз; `onPaymentTimeout` недосяжний з HTTP-входу.
4. Кожен компонент, залежність і NFR трасується до lab1–lab4 (аудит); нові — названо й обґрунтовано.
5. Шари згори вниз: UI → API → сервіси → Data Access → БД; усередині межі залежності — лише вниз або в шарі сервісів, без циклів.
6. `spec.md` і `DEFENSE.md` — до сторінки.
