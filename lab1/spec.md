# Специфікація: ER-модель «Онлайн-магазин»

## 1. Мета і межі

Описати дані онлайн-магазину у вигляді концептуальної ER-моделі. Цей документ задає сутності, атрибути, ключі, зв'язки та критерії прийняття. Сама діаграма робиться наступним кроком. SQL не використовується.

## 2. Наскрізні правила моделі

| № | Правило |
|---|---------|
| R1 | Усі моделі в 3НФ: кожен неключовий атрибут залежить від ключа, від усього ключа і ні від чого іншого. |
| R2 | Усі ідентифікатори (`*_id`) мають один тип: **ціле додатне число**. |
| R3 | Первинний ключ сутності називається `<сутність>_id`. Зовнішній ключ на неї в будь-якій іншій сутності називається **так само**. |
| R4 | Назви атрибутів унікальні в межах моделі, крім ключів із R3. Тому `category_name`, `product_name`, а не просто `name`. |
| R5 | Зв'язок «багато-до-багатьох» показується як зв'язок M:N між двома сутностями, без сполучної (асоціативної) сутності. Атрибути зв'язку записуються на самому зв'язку. |
| R6 | Похідні значення (наприклад, сума замовлення) не зберігаються як атрибути. |
| R7 | Назви: англійською, `snake_case`, однина. |

## 3. Сутності

Позначення: **PK** — первинний ключ, **FK** — зовнішній ключ, **UQ** — унікальне значення.

### 3.1 customer (клієнт)

| Атрибут | Тип | Ключ / обмеження |
|---------|-----|------------------|
| customer_id | ціле | PK |
| first_name | текст | обов'язковий |
| last_name | текст | обов'язковий |
| email | текст | UQ, обов'язковий |
| phone | текст | необов'язковий |
| registered_at | дата й час | обов'язковий |

### 3.2 address (адреса доставки)

| Атрибут | Тип | Ключ / обмеження |
|---------|-----|------------------|
| address_id | ціле | PK |
| customer_id | ціле | FK → customer |
| country | текст | обов'язковий |
| city | текст | обов'язковий |
| street_line | текст | обов'язковий (вулиця, будинок, квартира) |
| postal_code | текст | обов'язковий |

### 3.3 category (категорія товарів)

| Атрибут | Тип | Ключ / обмеження |
|---------|-----|------------------|
| category_id | ціле | PK |
| category_name | текст | UQ, обов'язковий |

### 3.4 product (товар)

| Атрибут | Тип | Ключ / обмеження |
|---------|-----|------------------|
| product_id | ціле | PK |
| category_id | ціле | FK → category |
| product_name | текст | обов'язковий |
| sku | текст | UQ, обов'язковий (артикул) |
| description | текст | необов'язковий |
| price | число з копійками | ≥ 0, поточна ціна |
| stock_quantity | ціле | ≥ 0 |

### 3.5 order (замовлення)

| Атрибут | Тип | Ключ / обмеження |
|---------|-----|------------------|
| order_id | ціле | PK |
| customer_id | ціле | FK → customer |
| address_id | ціле | FK → address (куди доставити) |
| order_status | текст | одне зі значень: `new`, `paid`, `shipped`, `delivered`, `cancelled` |
| ordered_at | дата й час | обов'язковий |

### 3.6 payment (платіж)

| Атрибут | Тип | Ключ / обмеження |
|---------|-----|------------------|
| payment_id | ціле | PK |
| order_id | ціле | FK → order |
| payment_method | текст | `card`, `cash_on_delivery`, `bank_transfer` |
| payment_status | текст | `pending`, `succeeded`, `failed`, `refunded` |
| payment_amount | число з копійками | > 0 |
| paid_at | дата й час | необов'язковий (порожній, поки платіж не пройшов) |

### 3.7 review (відгук)

| Атрибут | Тип | Ключ / обмеження |
|---------|-----|------------------|
| review_id | ціле | PK |
| customer_id | ціле | FK → customer |
| product_id | ціле | FK → product |
| rating | ціле | від 1 до 5 |
| review_text | текст | необов'язковий |
| reviewed_at | дата й час | обов'язковий |

## 4. Зв'язки і кардинальності

| № | Зв'язок | Кардинальність | Участь |
|---|---------|----------------|--------|
| L1 | customer — address | 1 : N | клієнт має 0..N адрес; адреса належить рівно 1 клієнту |
| L2 | customer — order | 1 : N | клієнт робить 0..N замовлень; замовлення належить рівно 1 клієнту |
| L3 | address — order | 1 : N | на адресу 0..N замовлень; замовлення доставляється на рівно 1 адресу |
| L4 | category — product | 1 : N | у категорії 0..N товарів; товар належить рівно 1 категорії |
| L5 | order — product (**contains**) | **M : N** | замовлення містить 1..N товарів; товар є в 0..N замовленнях |
| L6 | order — payment | 1 : N | замовлення має 0..N платежів; платіж стосується рівно 1 замовлення |
| L7 | customer — review | 1 : N | клієнт пише 0..N відгуків; відгук має рівно 1 автора |
| L8 | product — review | 1 : N | товар має 0..N відгуків; відгук стосується рівно 1 товару |

### Атрибути зв'язку L5 (contains)

Зберігаються на зв'язку, не в `order` і не в `product`, бо залежать від пари «замовлення + товар».

| Атрибут | Тип | Обмеження |
|---------|-----|-----------|
| quantity | ціле | ≥ 1 |
| unit_price | число з копійками | ≥ 0, ціна товару на момент замовлення |

## 5. Обґрунтування 3НФ

- Усі сутності мають один простий ключ, тому часткових залежностей (2НФ) немає.
- Транзитивних залежностей немає: категорія винесена в `category`, адреса в `address`, а не повторюються в `product` і `order`.
- `unit_price` залежить від пари (замовлення, товар) і не дублює `product.price`: це знімок ціни на момент покупки.
- Сума замовлення не зберігається (R6), її можна обчислити з `quantity` і `unit_price`.
- Припущення для `address`: `postal_code` не вважається таким, що однозначно визначає `city` (один індекс може охоплювати кілька населених пунктів).
- Припущення для `order_status`, `payment_method`, `payment_status`: це обмежені набори значень, окремі довідники не потрібні, бо додаткових атрибутів у них немає.

## 6. Критерії прийняття

**Структура**
- AC1. У моделі рівно 7 сутностей: customer, address, category, product, order, payment, review.
- AC2. Кожна сутність має PK з іменем `<сутність>_id`.
- AC3. Усі 8 зв'язків (L1–L8) показані з кардинальністю та участю.

**Ключі та імена**
- AC4. Усі `*_id` мають однаковий тип: ціле додатне число.
- AC5. Кожен FK має ту саму назву, що й PK сутності, на яку він посилається (наприклад, `customer_id` в `address`, `order` і `review`).
- AC6. Поза ключами жодна назва атрибута не повторюється в різних сутностях.
- AC7. Усі назви відповідають правилу R7.

**Нормалізація**
- AC8. Кожна сутність у 3НФ; для кожної можна назвати функціональні залежності та показати, що транзитивних немає.
- AC9. Немає похідних атрибутів (сума замовлення, середній рейтинг тощо).

**Зв'язок M:N**
- AC10. Зв'язок order — product показаний як M:N напряму, без окремої сутності-посередника.
- AC11. Атрибути `quantity` і `unit_price` позначені як атрибути цього зв'язку.

**Обмеження даних**
- AC12. Для `email`, `sku`, `category_name` вказано унікальність.
- AC13. Для `price`, `stock_quantity`, `quantity`, `unit_price`, `payment_amount`, `rating` вказані допустимі діапазони.
- AC14. Один клієнт може залишити не більше одного відгуку на один товар (унікальна пара `customer_id` + `product_id` в `review`).

**Оформлення**
- AC15. У специфікації та в моделі немає SQL.
- AC16. Усі сутності, атрибути й зв'язки з цього документа присутні на діаграмі, і навпаки: на діаграмі немає нічого, чого немає тут.

## 7. Поза межами

Знижки й промокоди, склад із кількома локаціями, постачальники, кошик, ієрархія категорій, історія змін цін. Усе це можна додати окремо, але в поточну модель не входить.
