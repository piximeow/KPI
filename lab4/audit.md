# Аудит процесу

Відповіді чату й рішення за кожною знахідкою — `ai/prompts.md` (П1, П2). Кожне виправлення спершу змінювало spec, потім діаграму.

## 1. Переходи, досяжність, умови
- **Кінці:** `NoAddress`; Клієнт закрив форму; для `cash_on_delivery` — кінці потоку обох гілок після `commit` (Клієнта й Магазину); для картки — `stop` після `onPaymentTimeout` (гілка Клієнта теж закінчується кінцем потоку). Кожен досяжний від `start`.
- **Відмови після «Підтвердити»** (REQ-20, 19, 08, 07, 09, 06) повертають до форми — дій без виходу немає.
- **Кожен `if`** має гілку на кожне значення: адреса є/немає, натиснув/закрив, умова відмови так/ні, бракує/ні, збій/ні, `Refused`/ні, спосіб оплати (у гілці Клієнта і в гілці Магазину), подія шлюзу/таймера, підпис, `pending`, результат `succeeded`/`failed`.
- **Досяжність кожної гілки циклу:** недійсний підпис — S05 рядок 4; не `pending` — S05 рядки 1–3; успіх — S02; відмова банку — S03 рядок 1; таймер з `pending` — S03 рядок 3; таймер після успіху — S03 рядок 4.
- **Завершення циклу:** вихід лише після `onPaymentTimeout`, який приходить завжди (за припущенням, розділ 5; таймер поставлено до `commit`) — `adr/0002`.

## 2. Паралельні гілки
Після `commit` — `fork` у Магазині: гілка Клієнта (`OrderCreated` → вкладений `fork`/`join` дій `CheckoutUI`: `clearCart` ∥ номер або перехід на шлюз) закінчується кінцем потоку (⊗); гілка Магазину — цикл подій для картки. Для готівки гілка Магазину теж закінчується кінцем потоку, тож `stop` не обриває дій Клієнта. Зовнішній `join` чекає лише гілку Магазину, тож браузер, закритий після `OrderCreated`, не зупиняє обробку `onPaymentTimeout`. Вкладений `join` чекає лише дій `CheckoutUI` без очікування.

## 5. Залишкові розбіжності з lab2 і lab3
- **Паралельність:** у lab3 `clearCart` і показ номера / перенаправлення йдуть підряд; lab2 порядку не задає, тож у процесі вони паралельні.
- **Оплата на сторінці шлюзу** (S02, «Клієнт вводить дані картки») — поза процесом магазину.
- **Вибір першої події:** у lab3 події одного `payment` впорядковує `critical`; в activity — цикл з вибором за подією (`adr/0001`).
- **Друга вкладка:** повтор «Підтвердити» з другої вкладки створить другий `order` — розбіжність lab2, записана в `lab3/audit.md`.
- **Таймер після перезапуску:** повторна постановка для `pending` — припущення з `lab3/adr/0002`, у lab2 вимоги немає.

## Топ-3 розбіжності, виправлені через spec (було → стало)
1. **`join` чекав дії шлюзу** ↔ REQ-13: було — гілка `fork` закінчувалась дією шлюзу; стало — `join` не чекає іншого учасника (гілка Клієнта — кінець потоку).
2. **Залишок і сума поза транзакцією** ↔ S01, S04, REQ-07: було — перевірки до транзакції; стало — після `lockForUpdate`, з `rollback`.
3. **Таймер після `commit`** ↔ S02, `lab3/adr/0002`: було — після `commit`; стало — до `commit`.
